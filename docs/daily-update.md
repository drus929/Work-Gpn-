# Ежедневный сбор публикаций

Workflow [Daily incident source monitor](https://github.com/drus929/Work-Gpn-/actions/workflows/daily-update.yml) запускается ежедневно в **09:00 по Москве** (`0 6 * * *` UTC). Доступен ручной запуск **Run workflow** из `main`. После подготовки данных он явно запускает отдельный [Deploy published Pages build](https://github.com/drus929/Work-Gpn-/actions/workflows/deploy-pages.yml) из `gh-pages`. Планировщик GitHub может запускать задания с задержкой; точное время отражено на сайте. Расписание действует для workflow в основной ветке репозитория. Событие `push` запуск не вызывает, поэтому служебные коммиты не создают рекурсивных обновлений.

## Что обновляется

Скрипт `scripts/update-incident-monitor.py` запрашивает две открытые выдачи Google News RSS: русскую и английскую. Берутся публикации за последние **48 часов до начала сбора**. В JSON сохранены точные UTC-границы и их представление по Москве. Это окно поиска публикаций, отдельное от месячного окна подтверждённых событий на карте. Даты RSS сверяются с точным интервалом: более ранние, будущие, неправильного года и непонятные даты исключаются. Дата RSS не устанавливает дату самого происшествия или подлинную дату оригинала статьи.

Из выдачи выбираются до 16 последних уникальных ссылок. Число пропущенных из-за лимита сохраняется отдельно. Ссылки Google News разрешаются до оригиналов через публичную переадресацию или публичный механизм Google News; при изменении этого механизма ошибка остаётся в данных. Затем выполняется ограниченная проверка HTTP-доступности страниц. Совпадающие URL, в том числе с метками `utm_*`, не считаются разными публикациями. Разные статьи, переводы и перепечатки **не** признаются независимыми автоматически.

Результат — `src/data/incident-monitor.json`. Сохраняются только издание, дата из RSS, ссылки, этапы и время проверки доступности. Заголовки, тексты статей, фотографии и технические оценки повреждений не копируются. Все результаты имеют `reviewStatus: "unreviewed"`. Никакого автоматического вывода об ущербе, остановке, восстановлении или текущей работе предприятия нет.

**Подтверждённые записи `incidentRecords`, их описания и цвета карты скрипт не меняет.** Для изменения журнала по-прежнему нужны чтение оригиналов и редакционная проверка российских и западных независимых цепочек, отдельно для события и производственных последствий. Кросспостинг и пересказ заявления не создают нового подтверждения.

## Доступность и ошибки

`status` относится только к сбору RSS:

- `never_run` — запуск ещё не выполнялся;
- `complete` — обе выдачи получены и разобраны; это не редакционная проверка и не гарантия чтения всех оригиналов;
- `partial` — получена только часть выдач;
- `failed` — ни одну выдачу получить и разобрать не удалось.

У каждой выдачи сохранены `checkedAt`, HTTP-код и отдельная причина сетевой ошибки, отказа сервера или некорректного RSS. У каждой ссылки отдельно записаны результат разрешения оригинального URL и `availability`: `available`, `blocked`, `unavailable` или `unresolved`. `available` означает только получение достаточно содержательной HTML-страницы. Это не удостоверяет полноту или достоверность статьи. Явные капчи, формы проверки браузера, подписочные ограничения и короткие JavaScript-заглушки отмечаются как недоступные, в том числе при HTTP 200. Автоматическое распознавание ограничений тоже может ошибаться.

Время `availability.checkedAt` относится к текущей попытке получения оригинала. Если оригинальный URL не удалось определить, оно равно `null`: время чтения агрегатора не выдаётся за чтение статьи. При ошибках прошлые ссылки не копируются под новым временем. `lastSuccessfulRun` отдельно хранит дату, окно и счётчики последнего запуска, в котором были получены обе выдачи; при частичном или полном отказе этот снимок не обновляется. Полные результаты прошлых запусков остаются в истории Git.

Пустая выдача, частичный охват и сетевые отказы **не означают отсутствие инцидентов**. Время последнего успешного сбора также не является датой завершённой редакционной проверки. Истечение месяца не подтверждает восстановление.

Ограничения одного запуска: до 240 секунд, до 16 оригиналов, 10 секунд на сетевой запрос, не более одной повторной попытки при временном сетевом отказе/408/429/5xx и интервал не менее 0,35 секунды между запросами. Выдачи RSS и страницы изданий ограничены 512 КиБ на ответ; для служебной HTML-страницы разрешения Google News допускается до 1 МиБ, поскольку метаданные ссылки могут находиться после большого интерфейсного блока. Скрипт использует стандартную библиотеку Python и открытые источники; ключи новостных сервисов и LLM не нужны.

## Публикация и защита изменений

Основной workflow запускает Python-тесты сборщика, собирает данные, проверяет JavaScript-тестами уже обновлённый набор и собирает production-сайт. В `main` коммитится только новый JSON мониторинга, если он изменился. Содержимое `dist` коммитится в существующую `gh-pages` с сохранением её истории, `.nojekyll` и возможного `CNAME`. Дополнительно туда копируется `.github/workflows/deploy-pages.yml` из `main`: GitHub требует наличие этого workflow в основной ветке для регистрации и в выбранной ветке для запуска.

Две ветки отправляются одним `git push --atomic`, без `--force`. Перед отправкой проверяется, что удалённые `main` и `gh-pages` сохранили исходные SHA, а скрипт не изменил редакционный журнал и правила оценки. Любое параллельное изменение останавливает отправку; нужно повторить запуск от свежей `main`.

После отправки встроенный токен явно вызывает `workflow_dispatch` второго workflow на `gh-pages`, передавая ожидаемый SHA сборки. Именно этот разрешённый тип события может запускаться встроенным `GITHUB_TOKEN`. Второй workflow сверяет SHA события с ожидаемым SHA, берёт зафиксированный коммит `gh-pages` и загружает его как Pages artifact, исключая служебные `.git` и `.github`. Перед развёртыванием он повторно проверяет, что в `gh-pages` не появилась более новая сборка. Сбор и публикация используют разные последовательные группы concurrency (`daily-collection` и `pages-publication`), не отменяют работающие задания и не блокируют друг друга. Ни один workflow не запускается автоматически по `push`.

Развёртывание выполняется из `gh-pages`, что соответствует существующему ограничению окружения `github-pages`. Разрешать публикацию из `main` не требуется. Успех первого workflow означает подготовку и отправку сборки; фактическая публикация подтверждается успешным вторым workflow и проверкой URL сайта. При необходимости повторить только развёртывание можно вручную запустить **Deploy published Pages build**, обязательно выбрав ветку `gh-pages`.

При ошибке тестов, сборки или скрипта до формирования результата сайт не публикуется. Если обе RSS-выдачи недоступны, скрипт всё равно формирует явный результат `failed`; после успешных проверок сайт может опубликовать именно это уведомление с отдельной прошлой успешной датой. В конце такой запуск помечается ошибкой в Actions. Отказ публикации оставляет ранее развёрнутый сайт; изменения веток и состояние Pages всегда проверяются отдельно.

Для реального развёртывания используется `actions/deploy-pages`, потому что коммит в `gh-pages`, отправленный встроенным `GITHUB_TOKEN`, сам по себе обычно не запускает сборку Pages. Нужна однократная настройка существующего сайта:

1. Существующий сайт должен использовать **Source: GitHub Actions** (`build_type: workflow`). В начале запуска workflow получает текущую конфигурацию и, если нужно, пытается изменить только `build_type` существующего сайта через стандартный Pages API со встроенным токеном. Новый сайт не создаётся, домен и политика окружения не меняются. Если API отказывает в доступе, выполнение останавливается до изменения веток; тогда владелец выбирает Source в Settings → Pages и повторяет запуск. Существующий URL сохраняется; `gh-pages` продолжает хранить готовую сборку.
2. В окружении `github-pages` должна быть разрешена существующая ветка `gh-pages`. Текущая политика, ограничивающая развёртывание этой веткой, сохраняется.
3. Основной workflow использует встроенный `GITHUB_TOKEN` с `contents: write`, `actions: write`, `pages: write`. Workflow публикации имеет `contents: read`, `pages: write`, `id-token: write`. Дополнительных секретов нет. Политика организации/репозитория должна разрешать эти права.

Workflow проверяет `build_type` перед изменением веток и сообщает конкретную ошибку, если переключение или проверка недоступны. Наличие файлов workflow в репозитории само по себе не означает, что права и публикация уже проверены. Фактический запуск обоих workflow и проверка URL сайта подтверждают активацию; даты и ссылки доступности на сайте появляются только после сборки и развёртывания.

## Локальный запуск

```sh
python3 -m unittest discover -s tests -p 'test_incident_monitor.py' -v
python3 scripts/update-incident-monitor.py
node --test tests/*.test.js
npm run build
```

Параметры при необходимости: `--output /tmp/incident-monitor.json`, `--max-articles 16`, `--timeout 10`, `--deadline-seconds 240`. Полный отказ выдач возвращает код 2 после записи JSON, частичный сбор — код 0 с явным `status: partial`. Локальный запуск сам ничего не коммитит и не публикует. Первоначальный файл со статусом `never_run` не считается выполненной проверкой.
